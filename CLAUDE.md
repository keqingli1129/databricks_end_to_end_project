## Commands

Everything uses `uv` (Python 3.12 only, per `pyproject.toml`) and the Databricks CLI. The `DEFAULT` profile points at the bundle's workspace host. Pass `--profile <name>` explicitly, and don't pick a profile for the user.

```bash
uv sync --dev                                   # install deps (pytest, ruff, databricks-connect 18.0, databricks-dlt); versions pinned by `databricks environments setup-local`, don't hand-edit that block
uv run pytest                                   # run all tests (needs workspace auth, see below)
uv run pytest tests/sample_taxis_test.py::test_find_all_taxis   # single test
uv run ruff check . && uv run ruff format .     # lint / format (line-length 120)

databricks bundle validate --profile <p>        # check bundle config
databricks bundle deploy --profile <p>          # deploy to dev (the default target)
databricks bundle deploy -t prod --profile <p>  # deploy to prod
databricks bundle run sample_job --profile <p>  # run the job
databricks bundle run databricks_end_to_end_project_etl --profile <p>   # run the pipeline
databricks bundle run databricks_end_to_end_project_etl --refresh <table_name> --profile <p>  # refresh one dataset
databricks bundle run telematics_ingestion --profile <p>   # ingest new telematics into bronze
databricks bundle run telematics_simulator --profile <p>   # send 50 fake events (sink per var.telematics_source)
uv run simulate --dry-run --count 5                        # print fake events locally, no Databricks/Kafka
databricks bundle run seed_source_database --profile <p>   # create/fill the CDC source tables (safe to re-run)
databricks bundle run cdc_ingestion --profile <p>          # apply source inserts/updates/deletes to bronze
uv run python src/object_storage/prepare_files.py          # local: rewrite image-metadata IDs to part 2's, make schema-demo CSVs
databricks bundle run object_storage_ingestion --profile <p>   # Auto Loader: training_images, claim_images_metadata
databricks bundle run ingest_claim_images --profile <p>        # notebook: claim_images + cleanSource archive
databricks bundle run transformations --profile <p>           # bronze -> silver (data quality checks) -> gold
databricks bundle run smart_claims_end_to_end --profile <p>   # everything: 4 ingestion tasks in parallel, then transformations (~6 min)
databricks bundle run damage_classifier --only <prepare_images|train_and_register|batch_inference> --profile <p>  # ML steps; train_and_register creates a NEW model version
databricks bundle run claims_app --profile <p>                # deploy the code to the app and start it (it stops itself after 24 h)
databricks apps stop e2e-claims-dev --profile <p>             # stop the app
```

## Tests run against a remote workspace

There is no local Spark. `tests/conftest.py` starts a **Databricks Connect** session in `pytest_configure`, before any test is collected. If no cluster or serverless ID is configured, it falls back to serverless (`DATABRICKS_SERVERLESS_COMPUTE_ID=auto`). So every test run needs valid CLI auth and network access. Tests read real Unity Catalog tables such as `samples.nyctaxi.trips`. Fixtures:

- `spark`: the Databricks Connect session.
- `load_fixture("name.json|csv")`: loads a file from `fixtures/` as a DataFrame.

The shell sources ROS 2 Jazzy, which sets `PYTHONPATH=/opt/ros/jazzy/...`. pytest then autoloads ROS's `launch_testing` plugin, which fails with `No module named 'yaml'`. Run tests with that variable cleared: `env -u PYTHONPATH uv run pytest`.

Library code imports `spark` from `databricks.sdk.runtime`, so the same module works in local tests, in the wheel job task and in notebooks.

## Architecture

This is a Databricks Declarative Automation Bundle (formerly Asset Bundle) built from the `default-python` template. `databricks.yml` defines the bundle, pulls in `resources/*.yml`, and builds the package as a wheel with `uv build --wheel`.

- **Targets**: `dev` is the default and uses `mode: development`. Resources get a `[dev <user>]` prefix, schedules are paused, and the schema is `${workspace.current_user.short_name}`. `prod` deploys to a fixed user root path with schema `prod`. Its daily schedule is paused (`pause_status: PAUSED` in the job YAML). The UI can't pause bundle-managed jobs, so change it there and redeploy.
- **Catalogs**: each target sets its own catalog: `dev` uses `e2e_dev` and `prod` uses `e2e_prod`, with no default. **Bundles can manage catalogs, but this project deliberately doesn't.** Create a target's catalog by hand before its first deploy, with the UI or `CREATE CATALOG`. Don't add a `catalogs` resource. There are two reasons:
  1. **The bundle can't create them here.** This workspace uses Default Storage, so creating a catalog through the REST API, which is what bundles and `databricks catalogs create` use, fails with `Metastore storage root URL does not exist`.
  2. **Keeping them unowned protects the data.** A catalog created by hand could be adopted into the bundle with `bundle deployment bind`, but then `bundle destroy` would delete it.
- **Schema**: the bundle owns it (`resources/unity_catalog.yml`, which holds all project schemas and volumes), so `bundle destroy` deletes the schema and its tables. In `dev`, development mode renames it to `dev_<user>_<schema>`, so the job and pipeline must refer to `${resources.schemas.databricks_end_to_end_project_schema.name}`, not `${var.schema}`.
- **Shared package** (`src/databricks_end_to_end_project/`): plain Python that is built into the wheel. `main.py` is the `main` console entry point. It takes `--catalog`/`--schema` and runs `USE CATALOG/SCHEMA`.
- **Lakeflow Declarative Pipeline** (`src/databricks_end_to_end_project_etl/`): serverless, defined in `resources/databricks_end_to_end_project_etl.pipeline.yml`. Every file under `transformations/**` is loaded by a glob, so a new dataset file is picked up without changing any config. Convention: one dataset per file, using `from pyspark import pipelines as dp` with `@dp.table`. Datasets refer to each other by bare table name, resolved in the pipeline's catalog and schema. The pipeline YAML installs the project with `--editable ${workspace.file_path}`, **but that alone does not make `import databricks_end_to_end_project` work inside a pipeline**: the editable install's `.pth` file is never processed there, so `src/` is not on `sys.path`. The pipeline does put its `root_path` on `sys.path`, so any pipeline whose code imports the shared package needs `root_path: "../src"` (see `telematics_ingestion`). This template pipeline still has the narrower root path and works only because its transformations don't import the package. Because pipeline dependencies are cached during development, add pipeline-only libraries to the pipeline YAML's `environment`, not to `pyproject.toml`.
- **Job** (`resources/sample_job.job.yml`): runs once a day. `notebook_task` (`src/sample_notebook.ipynb`) runs first. Then two tasks run in parallel: `python_wheel_task`, which calls `main` from `../dist/*.whl`, and `refresh_pipeline`, which runs the pipeline.
- **Medallion schemas and landing volume** (`resources/unity_catalog.yml`): schemas `landing`, `bronze`, `silver`, `gold` (dev names them `dev_<user>_<layer>`; reference as `${resources.schemas.<layer>.name}`) and a managed volume `files` in landing. The bundle can create schemas and volumes inside the hand-made catalogs.
- **Telematics ingestion** (design and step-by-step plan in `docs/part1_kafka_ingestion_*.md`, source material `docs/transcript_1.txt`): pipeline `telematics_ingestion` (`resources/ingest_stream_telematics.pipeline.yml`, serverless, default schema bronze, `root_path: ../src`) with streaming tables `telematics_raw` → `telematics`. `var.telematics_source` picks the source for both the pipeline (`telematics.source` config) and the simulator job (`--sink`):
  - `files`: simulator JSON files in `/Volumes/<catalog>/<landing schema>/files/telematics/`, read with Auto Loader and reshaped into Kafka's columns.
  - `kafka` (**default since 2026-10-04**): Confluent Cloud via SASL_SSL/PLAIN, topic `telematics` (6 partitions; the chassis number is the message key, so each car keeps to one partition). Credentials live in the bundle-defined secret scope `kafka_<target>` (keys `bootstrap_servers`, `api_key`, `api_secret`; **`kafka_dev` holds the real values**, set with `databricks secrets put-secret <scope> <key>` at the prompt; never in git). The runbook is `docs/part1_task12_confluent_runbook.md`.
  - **Switching source** needs `bundle run telematics_ingestion --full-refresh-all`, **and then** `bundle run transformations --full-refresh telematics` (the full refresh rewrites `bronze.telematics`, which breaks the checkpoint of the streaming table `silver.telematics`), followed by a normal `transformations` run for gold (`--full-refresh <table>` updates only that table).
  - **Continuous mode is impossible in the dev target:** `mode: development` drops `continuous: true` from pipelines, and `presets.trigger_pause_status: UNPAUSED` is rejected. In dev, use a job with `continuous.pause_status: UNPAUSED` that re-runs the pipeline. For a real continuous pipeline, set it only for prod, as a target override.
  - Both sources produce the same columns, so `parse_telematics` (bronze keeps every field as a string; typing belongs in silver) works unchanged.
- **Telematics package** (`src/databricks_end_to_end_project/telematics/`): `events.py` (fake events), `kafka_config.py` (Spark and producer settings, secret reading), `parsing.py`, `simulator.py` (the `simulate` console script: `--dry-run`, `--sink files --landing-path …`, or `--sink kafka`). Tests exist only for `events` and `kafka_config`; the user chose to skip tests for the rest.
- **CDC ingestion** (design and step-by-step plan in `docs/part2_cdc_ingestion_*.md`, source material `docs/transcript_2.txt`). The transcript uses Lakeflow Connect from SQL Server, which can't run here: there's no reachable database, and its ingestion gateway needs classic compute, which Free Edition lacks. The stand-in:
  - **Source:** schema `source` (dev: `dev_<user>_source`) holds `customer` (key `customer_id`), `policy` (`policy_no`) and `claim` (`claim_no`), all with Change Data Feed on. Policies `POL0000001`–`10` use the part 1 telematics chassis numbers `CHS000001`–`10`.
  - **Seeding:** the job `seed_source_database` is a SQL task on `var.warehouse_id` (a `lookup` of "Serverless Starter Warehouse"). It runs `src/source_database/seed.sql`, which reads the `:catalog`/`:schema` named parameters, creates tables only if missing, and fills them only while empty.
  - **Never `DROP` or `CREATE OR REPLACE` the source tables.** That breaks the change feed; the fix would be a full refresh of `cdc_ingestion`.
  - **Pipeline:** `cdc_ingestion` (`resources/ingest_db_cdc_insurance.pipeline.yml`, bronze, config `cdc.source_schema`) has one file per table in `src/cdc_ingestion/transformations/`. Each is a `@dp.temporary_view` over `readChangeFeed` (minus `update_preimage`), then `dp.create_streaming_table` and `dp.create_auto_cdc_flow` (SCD Type 1, `sequence_by="_commit_version"`, deletes applied, change-feed columns excluded).
  - **Test:** `src/source_database/changes.sql` holds the insert/update/delete test for dev.
- **Object-storage ingestion** (design and step-by-step plan in `docs/part3_object_storage_*.md`, source material `docs/transcript_3.txt`):
  - **Volumes:** managed volumes in landing, `claims` (`images/`, `metadata/`, `archive/`, `_autoloader/`) and `training_images`. Their resource keys are `claims_volume` and `training_images_volume`.
  - **Raw files:** these live locally in `data/object_storage/`, which is gitignored and must never be committed (about 112 MB of images).
  - **The prepare script:** `src/object_storage/prepare_files.py` rewrites the metadata CSV's UUID `claim_no` and VIN `chassis_no` to part 2's `CLM%08d(n)` and `CHS%06d((n*7919)%12000+1)`. It writes the result, plus the schema-evolution demo CSVs, into `data/object_storage/prepared/`. Upload with `databricks fs cp` (paths need the `dbfs:/Volumes/...` prefix; a single-file `cp` needs the target folder to exist).
  - **Pipeline `object_storage_ingestion` (bronze):** `training_images` (cloudFiles `binaryFile`, 56 rows) and `claim_images_metadata` (cloudFiles csv, now `schemaEvolutionMode=rescue`: unknown columns go into `_rescued_data`; `new_column_1` exists from the earlier `addNewColumns` demo). Under `addNewColumns`, a new column makes `bundle run` print `Error: update cancelled`; the pipeline then starts a fresh update itself, with cause `SCHEMA_CHANGE`.
  - **Job `ingest_claim_images`:** runs the plain-PySpark notebook `src/object_storage/claim_images.py` (Databricks `.py` notebook source; widgets overridden by `base_parameters`). It reads cloudFiles `binaryFile` with a hand-set checkpoint and schema location under `claims/_autoloader/claim_images`, uses `trigger(availableNow=True)`, and writes to `bronze.claim_images`, a regular Delta table that no pipeline owns.
  - **Archiving:** `cleanSource=MOVE` to `claims/archive/`, with a 1-minute retention. Cleanup only happens during runs that have new files. A file moves once it was committed in an earlier run and is older than the retention, and only a limited batch moves per run. So expect files to move over the next one or two runs, not immediately.
- **Transformations** (design and step-by-step plan in `docs/part4_transformations_*.md`, source material `docs/transcript_4.txt`):
  - **Pipeline:** resource key `transformations`, displayed as **`e2e_transformations`**, because the separate `smart_claims_dev` bundle in this workspace already has a pipeline named `[dev <user>] transformations`, and pipeline names must be unique. Defined in `resources/transformations.pipeline.yml`: default schema silver, config `transformations.bronze_schema` / `transformations.gold_schema` (full names), `environment` with `geopy==2.4.1`. The same pin is in the `dev` group of `pyproject.toml`, so the editor resolves the import; keep both in sync.
  - **Code:** two files in `src/transformations/transformations/`, as in the transcript, not one per dataset.
  - **Silver (`bronze_to_silver.py`):** 7 tables, each with two `@dp.expect_all_or_drop` checks. `claim`/`policy`/`customer` are **materialized views** (batch reads), because a streaming read of an AUTO CDC target fails on its updates and deletes. `telematics` (typed from bronze's strings), `training_images` (with `label` from the file name), `claim_images` and `claim_images_metadata` (drops `_rescued_data`, `new_column_1`) are streaming tables.
  - **Gold (`silver_to_gold.py`):** MVs published by full name: `aggregated_telematics` (per car, with a geopy `geodesic` UDF for `distance_from_city_center_km`), `customer_claim_policy` (inner joins, so claims of deleted customers drop out), and `customer_claim_policy_telematics` (left join on `chassis_number`).
  - **Data quality numbers:** `databricks pipelines list-pipeline-events` doesn't include them. Use SQL: `SELECT origin.flow_name, details:flow_progress:data_quality FROM event_log('<pipeline id>') WHERE event_type = 'flow_progress'`. In the UI, they're behind the **"N met"** link in the update's Table metrics. The Catalog table's "Quality" tab is a different feature (Data Quality Monitoring).
  - **Job `smart_claims_end_to_end`:** runs `telematics_ingestion`, `cdc_ingestion`, `object_storage_ingestion` (`pipeline_task`) and the `ingest_claim_images` job (`run_job_task`) in parallel, then `transform` (`depends_on` all four, `run_if: ALL_SUCCESS`). Its hourly Quartz schedule is PAUSED; start it by hand. With no new data, a run is about 6 minutes, mostly serverless start-up.
- **Damage classifier** (design and step-by-step plan in `docs/part5_ml_*.md`, source material `docs/transcript_5.txt`). `resources/damage_classifier.yml` holds the experiment (key `damage_classifier_experiment`), the UC registered model (key `claims_damage_level`), the job `damage_classifier`, and the serving endpoint (key `claims_damage_level_endpoint`). Resource keys must be unique across **all** types, hence the suffixes.
  - **Dev names get prefixes:** the model is `<catalog>.dev_<user>_gold.dev_<user>_claims_damage_level`, and the endpoint is `dev_<user>_e2e-claims-damage-level`. Always pass names from resource references.
  - **Job tasks** (serverless notebooks in `src/ml/`): `01_prepare_images` (Pillow resize to 224×224 → `silver.training_images_resized`, plus a reachability check), then `02_train_and_register` (fine-tunes `microsoft/resnet-18` on CPU, logs to MLflow, registers a new version, and moves the **`prod` alias in code**; no `aliases` in YAML, or deploys would fight the notebook over it), then `03_batch_inference` (`mlflow.pyfunc.spark_udf(...@prod, env_manager="local")` → `gold.damage_predictions` plus a confusion matrix, and `gold.claim_image_predictions`).
  - **Notebook libraries:** `%pip install torch==2.5.1 transformers==4.46.3 mlflow==3.8.1 --extra-index-url https://download.pytorch.org/whl/cpu`. Hugging Face and pytorch.org are reachable from serverless here.
  - **The pyfunc** `DamageClassifier` takes a DataFrame column `content` (bytes, or base64 strings when served) and returns `ok`/`minor`/`major`.
  - **Endpoint:** pinned to a version via `entity_version` (currently "2"), CPU Small, scale-to-zero. The first request after idle times out (cold start, about 1 min); retry it. When a deploy fails with an early "Container image creation failed: internal error", the build-logs API is empty; read `databricks api get /api/2.0/serving-endpoints/<name>/events`. That error was transient once, and a redeploy fixed it.
  - **Local editor environment:** the main `.venv` dev group has `torch` (CUDA build, for the local RTX 5070) and `mlflow`, but **not `transformers`**: the setup-local constraint `huggingface-hub~=1.2.4` fits no transformers release. Laptop training (part 5 Task 7) needs a separate ML environment.
- **Consumption: claim checks, dashboard, Genie** (part 6a; design and step-by-step plan in `docs/part6a_consume_*.md`, source material `docs/transcript_6.txt`; the app is part 6b, below):
  - **`gold.claim_checks`** (MV at the end of `silver_to_gold.py`, one row per claim): the business rules are constants (`EXPECTED_DAMAGE`, `COVERAGE_LIMITS`, `MAX_SPEED_KMH`, `CHECKS`) imported from **`src/claims_app/claim_rules.py`**, the single copy that the app uses too, so the dashboard, Genie and the app agree. Checks: `severity_match` (claimed severity mapped to ok/minor/major vs `gold.claim_image_predictions`), `amount_within_limit`, `policy_valid`, `speed_ok` (≤150 km/h). A NULL check means "not run" and is not a failure; `failed_checks` lists the false ones; `claim_status` is `auto_approved` or `needs_review`. Every column has a comment (via the MV's `schema` DDL), which Genie reads.
  - **Resources** in `resources/claims_consumption.yml`. Titles start with **"E2E"**, because `smart_claims_dev` already has "Claims Investigation".
  - **Dashboard** `claims_investigation_dashboard`: `src/consumption/claims_investigation.lvdash.json`, with **bare table names** in its queries; `dataset_catalog: ${var.catalog}` / `dataset_schema: ${resources.schemas.gold.name}` point them at each target's gold. Two datasets (`claims`, `check_failures`) with DATE parameters `:start_date`/`:end_date`; each date-picker widget has one query per dataset so it filters both. A date picker only binds to a DATE-typed parameter. To pull UI edits back into the file: `databricks bundle generate dashboard --existing-id <id> --watch`.
  - **Genie space** `claims_genie_space`: inline `serialized_space` YAML, **not** a `.geniespace.json` file. Genie spaces have no `dataset_catalog`, and `file_path` contents are not interpolated, so table names and example SQL use `${var.catalog}.${resources.schemas.gold.name}.<table>`. Format rules: ids are 32 lowercase hex chars; id-keyed lists sorted by id, tables by identifier, `column_configs` by `column_name`; at most one `text_instructions` item. Genie joins the string lists into one string when it stores them; `bundle plan` still shows no drift.
  - **Practice versions** ("Practice – claims summary", "Practice – claims genie") were built by hand in the UI and are not in the bundle.
- **The claims app** (part 6b; design and step-by-step plan in `docs/part6b_app_*.md`). It's a Streamlit app, `e2e-claims-<target>`, with source in `src/claims_app/` and resources in `resources/claims_app.yml`. Customer mode submits a claim with a photo: the endpoint predicts the damage, `claim_rules.check_claim` runs the four checks, and the claim is saved. Admin mode has two tabs: Overview (counters and a filtered list, capped at 500 rows) and Analysis (one claim's photo and checks).
  - **Lakebase is shared:** Free Edition allows one project, and `smart_claims_dev`'s `smart-claims-dev` already holds it. This bundle only *references* its `production` branch and owns the database **`e2e_claims_<target>`** inside it. Dev mode doesn't prefix Postgres databases or app names, hence the target suffix. **Never `bundle destroy` the `smart_claims_dev` bundle while this app is wanted:** that deletes the project and our database with it.
  - **Synced tables** (`postgres_synced_tables`, CONTINUOUS): `gold.claim_checks` → `<gold schema>.claim_checks_pg`, and the MV `gold.policy_lookup` (one row per policy: limit, dates, `max_speed`) → `policy_lookup_pg`. Both share one sync pipeline through `existing_pipeline_id: ${resources.postgres_synced_tables.claim_checks_synced.status.pipeline_id}`. An MV can be a continuous source through automatic change data feed: give it the table property `pipelines.externalMetadata.enabled = true`, and set `pipeline_channel: PREVIEW` in the synced table's `new_pipeline_spec`. In Postgres, `failed_checks` is `jsonb`.
  - **The app's own data:** schema `app` with `app_claims` (claim numbers `APP%08d` from `app.claim_no_seq`; `failed_checks` is `jsonb` so admin mode can `UNION ALL` it with `claim_checks_pg`). The app's service principal creates and owns these on startup. Photos go to `claims/app_uploads/`; pipeline photos are in `claims/images/` or `claims/archive/`. App claims are not fed back into the lakehouse.
  - **Manual GRANT:** the app's service principal must be allowed to read the synced tables. As yourself, in database `e2e_claims_<target>`, run `GRANT USAGE ON SCHEMA <gold schema>` and `GRANT SELECT ON ALL TABLES IN SCHEMA <gold schema>` `TO "<app service principal client id>"`. Bundles can't do this. Redo it if a synced table is recreated or the app gets a new service principal.
  - **App gotchas:**
    - The `postgres` app resource injects `PG*`, but **not `LAKEBASE_ENDPOINT`**. That comes from `var.lakebase_endpoint` in the app's `config.env`.
    - The bundle's `config` (command and env) replaces an `app.yaml`, and unlike `app.yaml` it understands `${...}`.
    - Streamlit flags `--server.enableWebsocketCompression=false` (otherwise the page loops between "Connecting" and "Running" behind the Apps proxy) and `--server.enableXsrfProtection=false --server.enableCORS=false` (otherwise uploads fail with a 400).
    - `streamlit==1.65.0` is pinned in `requirements.txt` and in pyproject's dev group. Keep the two in sync.
    - `$` in `st.write` text must be escaped as `\$`.
    - A failed `@st.cache_resource` call isn't cached, so `get_pool()` closes a pool whose setup fails.
    - Logs are only in the UI (Compute → Apps → Logs), because `databricks apps logs` needs OAuth and the profile is a token.
  - **Pause and resume** (to save cost): `databricks apps stop e2e-claims-dev`, `databricks pipelines stop <sync pipeline id>`, and disable the shared compute with `databricks postgres update-endpoint projects/smart-claims-dev/branches/production/endpoints/primary spec.disabled --json '{"spec": {"disabled": true}}'`. Resume in reverse order: enable the compute, `databricks pipelines start-update <id>`, then `bundle run claims_app`. **While paused, every `bundle deploy` fails** at planning (`Endpoint … is disabled`), because reading the synced tables needs the compute. Enable it for the deploy, then disable it again. The stopped sync pipeline stays stopped.
- `explorations/` notebooks are gitignored, so treat them as scratch work.
